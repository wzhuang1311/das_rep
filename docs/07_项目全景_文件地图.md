## 零、先建立全局图景：一条从原始数据到结论的流水线

```
                          【原始数据】
                    das_data\train\*.mat  (12335 个)
                    das_data\test\*.mat   ( 3084 个)
                    das_data\train\label.txt  (文件名 + 标签)
                              │
        ┌─────────────────────┴─────────────────────┐
        │  第 ① 步：数据体检（写模型之前必须做）      │
        │  → data_profile.py                        │
        │  产出：一份"数据体检报告"（有什么病、要不要治）│
        └─────────────────────┬─────────────────────┘
                              │
        ┌─────────────────────┴─────────────────────┐
        │  第 ② 步：数据可视化（用眼睛确认）          │
        │  → stage1 的脚本（图已并入报告）            │
        │  产出：6 类事件时空图，确认"这些类真的有区别" │
        └─────────────────────┬─────────────────────┘
                              │
        ┌─────────────────────┴─────────────────────┐
        │  第 ③ 步：数据加载（把文件变成张量）        │
        │  SVM 路线 → get_das_data.py               │
        │  CNN 路线 → mydataset.py                  │
        └─────────────────────┬─────────────────────┘
                              │
        ┌─────────────────────┴─────────────────────┐
        │  第 ④ 步：模型                               │
        │  SVM → feature_extraction.py + sklearn     │
        │  CNN → models.py (网络) + 训练循环          │
        └─────────────────────┬─────────────────────┘
                              │
        ┌─────────────────────┴─────────────────────┐
        │  第 ⑤ 步：评估                               │
        │  → 混淆矩阵、precision/recall/F1            │
        └─────────────────────┬─────────────────────┘
                              │
        ┌─────────────────────┴─────────────────────┐
        │  第 ⑥ 步：出图与报告                          │
        │  → make_*.py 生成图表                       │
        │  → 复现报告.md / .docx                      │
        └─────────────────────────────────────────────┘
```

**关键认识**：**写模型只是第 ④ 步，前后各有两步同样重要。**
新手最常犯的错是直接从第 ④ 步开始（"抄个网络就跑"）。

## 一、文件地图：按"你该按什么顺序看"排列

### 第 0 层：环境与工具（先有这些才能干活）

| 文件 | 作用 | 什么时候用 |
|------|------|-----------|
| `env_check.py` | **环境自检**：检查 Python/torch/CUDA/依赖库是否就绪，并实测 GPU 能否做矩阵乘法和反向传播 | 换电脑、装完环境、出诡异错误时先跑这个 |
| `docs/01_环境配置_CUDA.md` | CUDA 环境搭建记录（含 cu128 无 py3.13 轮子等踩坑） | 换机器重装时 |
| `docs/02_第一步速查卡.md` | VSCode 操作步骤 + 报错对照表 | 换机器重装时 |
| `docs/03_为什么要虚拟环境.md` | 虚拟环境的原理与必要性 | 理解"为什么要多这一步" |

**为什么要有 `env_check.py`？**
深度学习项目出问题时，"环境坏了"和"代码写错了"的症状经常很像。
先跑环境自检，**排除掉一半可能性**，再去看代码——这是最高效的排查顺序。

### 第 1 层：数据体检（写任何模型之前）

| 文件 | 作用 | 输入 → 输出 |
|------|------|-----------|
| `data_profile.py` | **通用数据体检工具**。检查：文件完整性、形状/类型一致性、NaN、类别平衡、train/test 是否有重叠、死通道、坏样本 | `das_data\` → 体检报告（打印 + 存 `results\data_profile.txt`） |
| `docs/06_数据处理的为什么.md` | 讲清"数据清洗的三个动作：检测→判断→决策" | — |

**这个脚本的设计要点（以后换项目直接复用）**：

```python
DATA_ROOT = r"...\das_data"      # ← 换项目只改这些
CLASSES = {...}
FILE_PATTERN = "*.mat"
MAT_KEY = "data"
EXPECTED_SHAPE = (10000, 12)
SPLITS = ["train", "test"]
```

**它是"通用"的**——CONFIG 区域集中了所有项目相关的常量，
换数据集时只需要改这几行。**这是写工具脚本的正确姿势。**

**为什么第一步是体检而不是写模型？**
`06_数据处理的为什么.md` 里那句话很到位：
> 新手最大的错误：直接跳到第 ④ 步，结果模型不收敛，然后花三天调参——
> 其实问题出在第 ②③ 步。

### 第 2 层：数据加载（把磁盘文件变成模型能吃的张量）

这里有**两条独立路线**，因为 SVM 和 CNN 对数据的组织方式完全不同。

#### SVM 路线：一次性读入内存的大矩阵

| 文件 | 作用 | 输入 → 输出 |
|------|------|-----------|
| `get_das_data.py` | 读 `label.txt` → 逐个 `.mat` → 差分 → 提特征 → 拼成一个大矩阵 | `das_data\train\` → `X (12335, 384)`, `y (12335,)` |
| `feature_extraction.py` | **官方版**：对一条时序信号提 16 维手工特征 | `(10000,)` 或 `(9999,)` → `(16,)` |
| `reference_feature_extraction.py` | **向量化版**（我写的）：功能同上，快 9.6 倍，**逐位等价** | 同上 |

**为什么 SVM 要"一次性读入内存"，而 CNN 要"按需读取"？**

| | SVM | CNN |
|---|-----|-----|
| 数据形式 | 384 维向量 | 10000×12 原始矩阵 |
| 单个样本大小 | 384 × 4B ≈ 1.5 KB | 10000×12×4B ≈ 480 KB |
| 全部（15419 样本） | 约 **23 MB** ✅ 装得下 | 约 **7.4 GB** ❌ 装不下 |
| 做法 | 全读进内存，一次训练 | `Dataset` 按需读取，每次 100 个 |

**这是数据量决定架构设计的典型例子。**

#### CNN 路线：PyTorch 标准三层结构

| 文件 | 作用 | 说明 |
|------|------|------|
| `mydataset.py` | `class MyDataset(Dataset)` | 实现 `__init__` / `__len__` / `__getitem__`，是"怎么取一个样本"的定义 |
| `models.py` | `class CNN(nn.Module)` | 网络结构（论文 Table 3），7421 个参数 |

**`MyDataset` 三个方法的分工**（这是 PyTorch 的固定套路，以后每个项目都这么写）：

```python
def __init__(self, root_dir, names_file):
    # 只读"文件名列表"，【不读数据】—— 所以很快
    # 如果这里就 loadmat，15419 个文件要读很久，而且内存爆炸

def __len__(self):
    # 返回样本总数，DataLoader 靠它决定"一个 epoch 有多少个 batch"
    return self.size

def __getitem__(self, idx):
    # ★ 核心：被调用时才读第 idx 个文件
    # 读 .mat → 转类型 → 归一化 → 返回 {'data':..., 'label':...}
    # 这里是唯一碰磁盘的地方
```

**`DataLoader` 负责的三件事**（在 `das_data_cnn.py` 里调用）：

```python
train_loader = DataLoader(
    dataset=train_dataset,
    batch_size=100,        # ① 一次喂几个样本
    shuffle=True,          # ② 每个 epoch 打乱顺序（防止模型记住顺序）
    # num_workers=0        # ③ 用几个子进程读数据。官方没写 → 默认 0 → 单线程 → GPU 饿死
)
```

> **`num_workers` 就是我们发现的那个"GPU 利用率只有 3%"的直接原因**。
> 详见 `bug_记录.md` 的优化章节。

### 第 3 层：模型与训练

| 文件 | 作用 |
|------|------|
| `das_data_svm.py` | **官方 SVM 主程序**：读数据 → MinMaxScaler → SVC(rbf) → 混淆矩阵 → 指标 |
| `das_data_cnn.py` | **官方 CNN 主程序**：Dataset → DataLoader → 训练循环 → 评估 → 出图 |

**`das_data_cnn.py` 的三个函数（训练脚本的标准骨架）**：

```python
def train(model, train_x, train_y, optimizer, criterion):
    """一个 batch 的训练：前向 → 算损失 → 反向 → 更新参数"""
    _, probs = model(train_x)          # ① 前向传播
    loss = criterion(probs, train_y)   # ② 算损失
    loss.backward()                    # ③ 反向传播 ← 你鱼书学的那部分
    optimizer.step()                   # ④ 更新参数

def test(model, dataset, criterion):
    """评估：不更新参数，只统计"""
    model.eval()                       # ★ 切换到评估模式
    with torch.no_grad():              # ★ 不计算梯度，省显存
        ...

def main(args):
    # ①数据 ②模型 ③优化器+损失 ④训练循环 ⑤保存+出图
```

**`train` / `test` 的两个关键区别**（新手最容易漏）：

| | `train` | `test` |
|---|---------|--------|
| 模式 | `model.train()` | `model.eval()` |
| 梯度 | 要算（`loss.backward()`） | 不算（`torch.no_grad()`） |
| 参数 | 更新（`optimizer.step()`） | **不动** |

**为什么必须切换？** 因为 `Dropout`、`BatchNorm` 这类层在训练和推理时行为不同。
本项目的 CNN 没有这些层，所以切换**看起来**没影响——**但这是必须养成的习惯**，
以后用 ResNet 之类一定会踩。

### 第 4 层：评估与出图

| 文件 | 作用 | 输入 → 输出 |
|------|------|-----------|
| `make_svm_report.py` | 由 SVM 混淆矩阵生成对比图 | 硬编码矩阵 → `svm_confusion_ours.png`, `svm_vs_paper.png` |
| `eval_cnn.py` | **加载 `model.pth` 重新推理**，得到权威混淆矩阵 | `model.pth` → `cnn_confusion_true.png` + CSV |
| `make_cnn_report.py` | 由日志解析结果生成 CNN 对比图 | `result.log` → `cnn_vs_paper.png` |
| `make_lda_figure.py` | LDA 降维可视化（论文 Fig. 5） | 特征 CSV → `lda_*.png` |
| `make_seed_summary.py` | 多种子实验统计与对比图 | `seed_runs\*.log` → `cnn_seed_stats.png` |

**`eval_cnn.py` 为什么重要？（一个真实的教训）**

当时我试图从日志里的"列和"反推 CNN 的混淆矩阵，结果**算出来自相矛盾**
（对角线和 2813，但日志的 acc 要求 2865）。

**正确做法是不要猜——直接重新推理一次**：

```python
model = torch.load('model.pth')         # 加载训练好的权重
# 在测试集上跑一遍，收集预测结果
C = confusion_matrix(labels, preds)     # 得到权威矩阵
```

**教训**：**有"重新算一遍"这条路时，就不要用推算。**
推算容易在某个环节出错，而且错了不容易发现。

### 第 5 层：性能与可靠性工具

| 文件 | 作用 |
|------|------|
| `bench_dataloader.py` | **数据加载性能基准**：对比官方双层 for 循环 vs 向量化 |
| `run_svm_fast.py` | 用向量化特征提取跑完整 SVM 流程 |
| `run_cnn_seeds.py` | **多种子重复实验**：固定种子 → 训练 → 汇总均值±标准差 |
| `seed_runs\_single_run.py` | 上面脚本自动生成的单次训练模板 |

**`run_cnn_seeds.py` 的设计思路值得学**：

```
主进程（run_cnn_seeds.py）
   │  ① 把"单次训练脚本"作为字符串写成一个 .py 文件
   │  ② 对每个种子，用 subprocess 启动一个新 Python 进程
   │  ③ 从日志文件读结果，汇总统计
   ▼
子进程（_single_run.py --seed 1 / 2 / 3）
   └─ 固定种子 → 训练 → 把结果写进日志
```

**为什么不直接在循环里训练三次？**
因为**进程隔离**：`torch.manual_seed()` 只能保证"从头开始"的可复现性，
但如果三轮在同一个进程里跑，前一round 的显存状态、CUDA 上下文可能影响后一轮。
**每轮开新进程，是保证实验独立性的标准做法。**

## 三、完整数据流：一个样本的旅程

以 CNN 路线的一个"挖掘"样本为例，走一遍全流程：

```
① 磁盘上
   das_data\train\02_dig\220104_sys_dig_01_single_data_1.mat
   里面：变量 data，uint16，形状 (10000, 12)

② DataLoader 请求第 idx 个样本
   → MyDataset.__getitem__(idx)
       ├─ 读 label.txt 第 idx 行 → 拿到路径和标签 "1"
       ├─ scio.loadmat(path)['data']        → (10000, 12) uint16
       ├─ .astype(int)                       → (10000, 12) int64
       └─ normalize(rawdata)                 → 每个样本独立归一到 0~255
                                             （论文 4.2 节："模拟灰度图"）
   返回 {'data': (10000,12) 数组, 'label': 1}

③ DataLoader 攒够 100 个样本
   → collate 成一个 batch: {'data': tensor(100,10000,12),
                            'label': tensor(100,)}

④ 训练循环把它变成卷积层要的形状
   batch_x = torch.unsqueeze(batch_x, dim=1)   → (100, 1, 10000, 12)
                              ↑ 插入"通道"维，因为 Conv2d 要求 (N,C,H,W)
   batch_x = batch_x.float()                   → 转 float32（卷积要求）
   batch_x = batch_x.cuda()                    → 搬到 GPU

⑤ 模型前向
   conv1: Conv2d(1→5, (200,3), (50,1)) → ReLU → MaxPool → (100,5,99,7)
   conv2: Conv2d(5→10, (20,2), (4,1))  → ReLU → MaxPool → (100,10,10,4)
   flatten                                               → (100, 400)
   Linear(400→6)                                         → (100, 6)   ← 6 类得分

⑥ 算损失、反向传播、更新参数
   loss = CrossEntropyLoss(得分, 标签)
   loss.backward()          ← 自动求导，算每个参数的梯度（鱼书里的反向传播）
   optimizer.step()         ← Adam 用梯度更新参数

⑦ 50 个 epoch 后，在测试集评估
   → 混淆矩阵 → precision/recall/F1 → 出图 → 报告
```

**SVM 路线在 ② 之后就分岔了**：

```
② → get_das_data.py
      ├─ 对 12 个通道各提 16 维特征（原始信号）
      ├─ 对差分信号再提一遍（12×16）
      └─ 拼成 384 维向量
    → 所有样本拼成大矩阵 (12335, 384)
    → MinMaxScaler 归一化
    → svm.SVC(kernel='rbf').fit(X, y)
```

## 四、关键的"为什么"：文件设计的取舍

### 取舍 1：为什么有两个特征提取文件？

| | `feature_extraction.py` | `reference_feature_extraction.py` |
|---|------------------------|----------------------------------|
| 来源 | 官方的 | 我重写的 |
| 速度 | 0.0146 秒/次 | 0.0015 秒/次（9.6 倍） |
| 用途 | **对比基准** | **实际使用** |

**保留两个版本的理由**：**没有对照，就无法证明优化没改结果。**
我用 504 次逐位对比证明两者输出完全一致（最大偏差 0.000000000000）。

**这个习惯以后要一直保持**：改代码前先留一份原始版本。

### 取舍 2：为什么 `das_data_cnn.py` 里 `num_workers` 没改？

官方代码没写 `num_workers`（默认 0）。我们可以改成 4 让它更快，
**但向量化之后已经不需要了**：

```
数据加载：15.24 秒/batch  →  0.09 秒/batch
GPU 计算： 0.48 秒/batch

优化前：CPU 是瓶颈（15.24 > 0.48）
优化后：GPU 是瓶颈（0.48 > 0.09）← 已经"喂饱"了，不用再并行
```

**工程原则**：**先优化写法，再考虑加资源。**
多进程是在"写法已经最优但还不够"时才用的手段。

### 取舍 3：为什么 `dif_qiaodu` 那个可疑特征没有改？

我发现官方那个特征的算法有数值疑点（官方内部得到 9.43e10，
任何 float64 计算得到 4.71e12，差 50 倍），但**查不清机制**。

**最终决定：保留官方写法。** 理由：

> **优化的前提是"不改数值"。一个自己都没搞清的地方，
> 不该在优化里顺手改掉。** 查不清的，就如实写"未完全查清"。

这比"我觉得它错了就改掉"更专业——因为一旦改了，
后面所有结果都无法与官方对照，**你也说不清差异是优化带来的还是改动带来的**。

## 五、复用指南：把这套结构搬到新项目

```
新项目/
├── data_profile.py          ← 改 CONFIG 区（路径/类别/文件名格式/形状）
├── env_check.py             ← 改数据路径
├── src/ 或 stage2/
│   ├── mydataset.py         ← 改 __getitem__ 里的"怎么读一个样本"
│   ├── models.py            ← 换成新网络
│   └── train.py             ← 改超参数、路径
├── tools/
│   ├── bench_dataloader.py  ← 通用，改路径即可
│   └── run_seeds.py         ← 通用
├── results/                 ← 所有输出
└── docs/
    ├── bug_记录.md          ← 新建
    └── 报告.md              ← 新建
```

**迁移时唯一需要动脑的地方**：
1. `data_profile.py` 的 CONFIG（数据长什么样）
2. `mydataset.py` 的 `__getitem__`（怎么读一个样本）
3. `models.py`（网络结构）

**其余全是通用的**——这就是"分层"的价值。
